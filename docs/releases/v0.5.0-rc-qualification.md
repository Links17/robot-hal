### Task 3 hosted-failure follow-up: camera runtime terminal replay

A Hosted CI failure exposed a camera runtime request/reap race: a camera worker
could publish `camera.session.unplugged` and begin cleanup while its session
still remained in the active map. A subsequent request passed lease validation
and was incorrectly admitted into the still-live command channel; cleanup then
rejected it as `runtime.session.closed` before `reap_when_finished` persisted
the terminal error in the closed-session map.

The terminal check alone was insufficient because it could race with
`try_enqueue`. Request admission now holds the same asynchronous `admission`
lock as native command execution while it rechecks closing and terminal state
and performs `try_send`. A worker holds that lock through terminal publication,
so terminal publication is ordered atomically against the terminal
check/enqueue pair. The lock is released before awaiting the command response;
no synchronous mutex is held across an await. The closed-channel fallback still
replays a terminal error when available and otherwise retains
`runtime.actor.unavailable`. This preserves queue-full, stale-lease, closing,
and other transport/actor behavior.

The deterministic regression runs a worker-owned terminal publisher that first
holds admission. A `cfg(test)` hook notifies the test only after the spawned
request has polled the admission mutex and received `Pending`; the test then
asserts that the request remains blocked before allowing the worker to publish
`camera.session.unplugged` through the production helper and release admission.
It asserts that `camera.capture` returns the canonical unplugged error and that
the live receiver remains idle. The hook is absent from non-test builds and
replaces the previous request-started-plus-yield assumption, so the assertion
does not depend on scheduling probability or sleeps. The original
check-then-enqueue implementation was observed RED with the request enqueued
after terminal publication and cleanup reporting `runtime.session.closed`; the
admission-locked implementation is GREEN.

All `terminal_error_tx` publication paths now use that same synchronous helper:
native terminal command results, cleanup close/mapping failures, and the
catch-unwind worker fallback. The helper requires the admission guard and does
not await while the guard is held. Native terminal errors retain priority over
cleanup errors, while cleanup and actor-unavailable fallbacks keep their prior
ordering.

### Task 3 hosted-failure follow-up: GPIO cancelled queued read

Hosted run `32189655160` flaked in
`gpio_cancelled_queued_read_does_not_start_native_io`. The production GPIO
runtime was not changed. The old test started a second `gpio_read` task,
yielded once, and then inferred that its request was queued. A scheduler could
instead leave that task unpolled, so the test neither proved queue admission
nor proved cancellation of an admitted command.

The regression test now uses a test-only GPIO queue-admission observer. After
the first native read blocks, it waits until the observer reports the second
request was admitted before aborting and awaiting its `JoinHandle` with
`JoinError::is_cancelled()`. Only then does it release the first native read.
The test retains its assertion that a second native read never starts and that
`close()` succeeds. The observer is gated behind the runtime crate's
`test-support` feature, so default production builds have no new public
behavior. This is a test-contract correction, not a change to GPIO runtime
behavior.

### Task 3 hosted-failure follow-up: CAN broker receive batching

A Hosted broker-contract failure exposed test scheduling dependence rather than
a production CAN defect. `max_frames` is an upper bound: a receive completes
as soon as one or more frames are available and returns the available prefix,
up to that limit. The actor implements this as
`min(max_frames, received.len())`; it must not wait to accumulate the requested
maximum.

The affected broker test previously sent a two-frame loopback batch and then
assumed a subsequent `receive(max_frames = 2)` would always observe both
frames. That is not a portable assumption: after the first loopback frame is
delivered, the receive is allowed to return a one-frame correlated response
before the second send is scheduled.

The test now opens the broker session before injecting two ordered frames.
It then drains them through two correlated `max_frames = 1` receive requests
before issuing the unrelated batch send. Those responses are an observable
synchronization point: both frames have reached the actor's per-session ring,
and their order, correlation, and absent timestamps are verified without a
sleep or an assumption that one actor poll drains two adapter frames. The test
still verifies the batch-send response, filter replacement, status response,
and absence of unsolicited ordinary-frame events. No production CAN behavior,
including the `max_frames` upper-bound contract, changed.

A focused runtime contract test explicitly locks the permitted short response:
with one injected frame, `receive(max_frames = 2, internal_timeout = 1s)`
returns that one frame before a 100 ms outer test deadline. The external
deadline is deliberately an order of magnitude shorter than the internal
receive timeout, proving the receive does not wait for the requested maximum
or its timeout once a frame is ready. Local evidence:

- `cargo test -p seeed-hal-runtime --test can_runtime receive_returns_available_frames_below_requested_maximum -- --exact` — passed.
- `cargo test -p seeed-hal-broker --test broker_contract can_classic_batch_receive_filter_and_status_use_correlated_responses_only -- --exact` — passed.

### Task 3 hosted-failure follow-up: CAN batch loopback coverage

The stabilized receive setup had inadvertently removed the end-to-end assertion
for the two frames emitted by the broker `CanSend` batch. The setup remains
unchanged: after the session opens, the test injects two frames and confirms
actor fanout with two correlated `max_frames = 1` receives. After `CanSend`,
the test now uses the same bounded, correlated one-frame receive requests to
collect each loopback frame independently. It verifies send order and payload
bytes (`[1]`, then `[2]`) and the testkit's host-monotonic timestamp
(`0`, `HostMonotonic`, `virtual-can`) for both frames.

This does not require `max_frames = 2` to be filled. Each receive treats
`max_frames` as an upper bound and has its existing 100 ms timeout; no sleep,
unbounded retry, or production CAN change was introduced. The initial RED
observation was an assertion mismatch, not a product defect: virtual CAN
loopback intentionally supplies a host-monotonic timestamp, whereas the two
test-injected synchronization frames have no timestamp. The corrected
assertion is GREEN on the existing production behavior.

### Task 3 hosted-failure follow-up: source-gate Python release checks

Hosted CI run `32178423155` failed nine release checks on Ubuntu. The first
failure was a macOS-target virtual-conformance CLI fixture expected to reject
its missing broker as `release.conformance.invalid`; because the implementation
checked the requested host before validating the supplied broker, Linux instead
reported `release.conformance.host`. The same ordering made the stable error
category dependent on the operating system for invalid inputs.

The other failures shared one root cause. The wheel validation installed the
candidate with `uv pip install --offline`, which still resolves declared
runtime dependencies from the UV cache. The source-gate test environment had
installed its project dependencies but did not retain a registry cache entry
for `protobuf==6.32.1`, so the candidate validation failed before the
post-validation candidate-identity checks ran. That masked the intended
external-write, directory-replacement, byte-replacement, and symlink
fail-closed assertions.

The release tool now validates all CLI inputs before assessing whether the
requested platform matches the current host. It retains `release.conformance.host`
only for otherwise valid invocations on the wrong host; invalid platform,
command/ref, and broker inputs consistently produce
`release.conformance.invalid` without disclosing the broker path. Wheel
validation prepares the exact `protobuf==6.32.1` pure-Python wheel named in
`bindings/python/uv.lock` before the candidate build. It fetches only that
lock-recorded URL and rejects the file unless its SHA-256 matches the
lock-recorded hash. Candidate verification itself is offline: it creates a
fresh isolated venv and installs the candidate plus that exact local protobuf
wheel with `uv pip install --offline --no-deps`. It never consults the
project's `.venv` or its installed site packages.

The verification interpreter uses `-I`, strips proxy variables, imports
`seeed_hal` and generated `hal_pb2`, verifies both package versions, checks
that the protobuf module is in the verification environment, and requires the
installed `protobuf` `RECORD` to be the exact normalized mapping in the
lock-bound wheel. Every non-`RECORD` entry needs a SHA-256 and byte size, every
installed entry is rehashed, and added, missing, duplicate, hashless, or
out-of-distribution-metadata entries fail validation before candidate output is
returned. Candidate wheel members are first parsed as safe POSIX relative
paths; a candidate is rejected if a normal member or the installed target of
its valid `.data/purelib/` or `.data/platlib/` member has normalized top-level
`google`, so it cannot shadow or extend the controlled namespace.

The downloaded locked wheel is staged in a private directory and the
candidate-directory identity and artifact byte/symlink checks execute after
validation. These checks are fail-closed for changed candidate output: a
substituted wheel cannot produce a successful candidate result because the
post-install exact-record verification and the before/after candidate checks
must both pass. They are not a same-UID process sandbox: pathname-consuming
tools such as `uv` cannot receive a no-replace guarantee from Python directory
permissions alone when an adversary has the same UID.

`package-python` is unsupported on Windows for the current RC candidate build;
the only completed local Python candidate evidence is Ubuntu/macOS-host
evidence recorded above. Windows workflow wiring remains a contract fixture
until Windows-hosted candidate evidence is recorded.
