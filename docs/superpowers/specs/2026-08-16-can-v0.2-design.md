# CAN/CAN FD v0.2 Design

**Status:** Approved in conversation; pending written-spec review

**Date:** 2026-08-16

**Scope:** Add a complete raw CAN/CAN FD vertical slice to Seeed HAL using a virtual conformance adapter, Linux SocketCAN, and Windows/Linux PCAN-Basic.

## 1. Objective

v0.2 adds business-independent raw CAN and CAN FD access while preserving the v0.1 architecture:

- the Rust library remains the implementation;
- the broker exposes the same semantics over local IPC;
- canonical physical identity remains distinct from a transient endpoint;
- sessions, leases, fencing, cancellation, cleanup, errors, and events remain shared HAL concepts;
- every queue and batch is bounded;
- device protocols and application meaning remain above HAL.

The broker release and affected crates advance to `0.2.0`. The wire contract remains major 1 and adds minor 1. A v0.2 broker supports wire `1.0..=1.1`; CAN operations require negotiated minor 1 and the relevant CAN capability.

## 2. Explicit non-goals

v0.2 does not implement:

- ISO-TP, J1939, CANopen, UDS, DBC decoding, or another higher-level/device protocol;
- scheduled transmission or cross-device clock synchronization;
- product concepts, motor control, safety sequences, or application workflows;
- USB, GPIO, Camera, Node bindings, or camera shared memory;
- remote networking, HTTP, or gRPC;
- silent fallback from CAN FD to Classical CAN;
- persistence of transient SocketCAN interface names or PCAN enumeration indices as strong identity.

## 3. Dependency strategy

Seeed HAL owns every public type and behavior. Third-party CAN types never appear in public Rust APIs, protobuf-independent Python APIs, or stable serialization.

Adapter implementations initially use:

- `can-hal-rs 0.4.2` for backend-neutral frame, filter, and status traits;
- `can-hal-socketcan 0.4.2` and its mature `socketcan` dependency for Linux frame I/O;
- the `socketcan`/netlink Rust API for querying and configuring Linux CAN links, never shelling out to `ip`;
- `can-hal-pcan 0.4.2` for Windows/Linux PCAN-Basic with runtime dynamic loading.

These versions satisfy the workspace MSRV. They are adapter-private implementation details. Before adoption, implementation must audit licenses, default features, blocking behavior, unsafe boundaries, and missing semantic coverage. If a backend package cannot satisfy a required invariant, the adapter may use the lower-level mature crate for that operation without changing the public design. No project-local fork is created unless an upstreamable defect requires one and is documented.

The PCAN-Basic vendor runtime remains an external deployment prerequisite. Its absence must not prevent a broker with optional PCAN support from starting.

## 4. Module boundaries

Only modules required for this vertical slice are added:

```text
crates/seeed-hal-can/       public CAN/CAN FD types and adapter traits
adapters/socketcan/         Linux SocketCAN discovery, configuration, and I/O
adapters/pcan/              Windows/Linux PCAN-Basic discovery, configuration, and I/O
crates/seeed-hal-runtime/   typed CanManager and per-resource shared actor
crates/seeed-hal-testkit/   VirtualCanAdapter and shared CAN conformance suite
crates/seeed-hal-protocol/  additive wire conversion
crates/seeed-hal-broker/    CAN request dispatch over the existing connection
crates/seeed-hal-client/    Rust broker CAN client
bindings/python/            Python broker CAN client
apps/seeed-hal-broker/      adapter composition, feature flags, and manifest
```

The runtime does not introduce a generic all-hardware actor hierarchy. `CanManager` is a typed seam parallel to Serial and reuses core contracts rather than duplicating them. The runtime accepts multiple CAN adapters concurrently so SocketCAN and PCAN discoveries can coexist.

The production broker composes Serial with every platform-appropriate enabled CAN adapter. Virtual adapters remain compile-time test/conformance dependencies and never masquerade as physical hardware in production manifests.

## 5. Public CAN model

### 5.1 Identifiers and frames

`CanId` is an enum with validated constructors:

- `Standard`: 11 bits, range `0x000..=0x7ff`;
- `Extended`: 29 bits, range `0x00000000..=0x1fffffff`.

`CanFrame` has explicit variants:

- `ClassicData { id, data }`, with `0..=8` payload bytes;
- `ClassicRemote { id, dlc }`, with no payload and DLC `0..=8`;
- `FdData { id, data, bitrate_switch, error_state_indicator }`, with `0..=64` payload bytes;
- `Error { classes, data }`, with one or more normalized transport error classes and at most 8 diagnostic bytes.

The normalized error-frame classes cover transmit timeout, lost arbitration, controller state, protocol violation, transceiver state, missing acknowledgement, bus-off, bus error, restart, and other. Raw diagnostic bytes are never stable decision fields.

Invalid IDs, payload lengths, remote-frame combinations, or flags fail during construction. CAN FD remote frames are prohibited. Classical frames never carry CAN FD flags. For data frames, the canonical payload length is the effective received length; the API does not expose a redundant raw DLC encoding. Remote frames retain DLC because they have no payload. The implementation never silently truncates or pads caller payloads.

### 5.2 Receive metadata and timestamps

`ReceivedCanFrame` contains a `CanFrame` and an optional `CanTimestamp`:

```text
CanTimestamp {
    timestamp_ns,
    source: Hardware | Kernel | HostMonotonic,
    clock_domain,
}
```

The adapter exposes the strongest timestamp it actually possesses. It returns `None` when it cannot make an honest timestamp claim. `clock_domain` is a bounded identifier scoped to one adapter/channel lifetime. Timestamps from different domains, different channels, or a reconnected actor are not implicitly comparable.

v0.2 does not schedule frames for future transmission and does not synchronize clocks. Those behaviors require future additive capabilities.

### 5.3 Filters

`CanFilter` expresses:

- CAN ID and mask;
- Standard, Extended, or either identifier format;
- data, remote, and error-frame classification.

Each session owns at most 64 filters. An empty filter set receives all supported frame classes. `replace_filters` atomically replaces one session's complete filter set; invalid input leaves the previous set unchanged.

The runtime always enforces filters in software per session. An adapter may install the union of active filters in hardware as an optimization only when doing so cannot remove a frame any session should observe. Hardware-filter reprogramming must not create observable false negatives; an adapter that cannot guarantee that property leaves hardware filtering permissive.

### 5.4 Bus status

`CanBusStatus` reports a normalized state (`Active`, `Warning`, `Passive`, `BusOff`, `Stopped`, or `Unknown`) plus optional receive/transmit error counters. Unsupported counters remain absent rather than fabricated. State transitions also use the existing owner-scoped transport health event path.

## 6. Open and configuration semantics

`CanOpenConfig` has two explicit modes.

### 6.1 Attach

`Attach` opens an already configured channel. It can state expected nominal bitrate, expected data bitrate, Classical/FD mode, listen-only state, and loopback state. Any stated expectation must be queried and verified. A mismatch returns `can.configuration.mismatch`; an adapter unable to query a stated expectation returns `can.configuration.unsupported`. HAL never silently changes configuration in Attach mode.

Attach supports shared operation:

- multiple Observe sessions may receive;
- at most one Control session may send and receive;
- Observe and Control may coexist;
- every operation carries the lease generation fencing token.

### 6.2 Configure

`Configure` supplies nominal bitrate, optional data bitrate, FD enablement, listen-only, loopback, and supported timing overrides. It requires a Maintenance lease and is exclusive for the entire session lifetime. The Maintenance session may send and receive after configuration succeeds, but no Observe or Control session may coexist.

The adapter snapshots the prior link state before mutation, applies the complete requested configuration, then queries and verifies the result before the session is exposed. Failure rolls back the provisional lease/generation and attempts to restore the prior state. Close also restores the prior state when the platform configuration is persistent. PCAN uninitialization satisfies restoration when configuration is channel-lifetime-scoped.

Restoration is compare-before-write where the platform exposes sufficient state, so HAL does not overwrite a configuration changed by an unrelated external process. A restore failure releases HAL ownership, emits a transport health event, and returns a structured cleanup error; it never claims restoration succeeded.

HAL exclusivity does not prevent unrelated external processes from opening or reconfiguring the bus. Adapters request OS/vendor exclusivity where available and report limitations.

## 7. Runtime ownership and concurrency

One runtime actor owns one physical CAN channel and its backend handle. The actor is keyed by canonical resource identity, not endpoint. It multiplexes all compatible Attach sessions and owns the single Maintenance session when reconfiguration is active.

Backend calls that may block run on the actor's explicitly owned worker, not on a Tokio executor worker. Cancellation and close have finite deadlines. If the backend cannot cancel a blocked call, the worker is terminally retired and the handle is released before the resource is exposed again.

Lease rules are:

- Observe: receive and query status, never transmit or configure;
- Control: transmit, receive, query status, and change its own filters;
- Maintenance: exclusive configuration plus transmit/receive/status/filter operations.

Stale generations, wrong owners, incompatible configurations, and unsupported capabilities fail before backend I/O. Opening a second Attach session must verify it is compatible with the live actor configuration. The runtime does not silently reconfigure a live actor.

## 8. Bounded data flow and backpressure

Each receiving session has a bounded ring of 256 frames by default. The configured capacity must be positive and remains bounded by an implementation hard limit documented in the interface.

When an RX ring is full, the actor drops the oldest frame, increments that session's dropped count, and continues servicing other sessions. The next `receive` for that session returns `can.receive.lagged` with bounded structured context containing the dropped count; it does not return frames in the same result. A subsequent receive returns the oldest retained frame. One slow observer never blocks the physical channel or another session.

The per-channel TX queue holds 64 frames by default and preserves FIFO order across callers. A single-frame send is one frame. `send_batch` accepts at most 64 frames and has atomic local admission: if the entire batch cannot fit, no frame from it is admitted and the call returns retryable `runtime.queue.full` with a committed count of zero.

Once admitted, a backend may accept a prefix before a later frame fails; physical transmission cannot be rolled back. Batch execution therefore returns either complete success or a typed `CanBatchSendError` containing the stable `HalError` and the exact committed prefix count. Callers never infer partial progress from a debug message or diagnostic context. Retrying an entire partially committed batch without application-level deduplication can duplicate frames.

A successful send means the backend accepted the frame for transmission. It does not mean another node acknowledged an application protocol or produced a response. Backend-reported bus/driver failures remain structured failures.

## 9. Broker and wire contract

Wire major 1 minor 1 adds protobuf messages and envelope variants for:

- enumerate/open/close CAN sessions;
- send one frame or a bounded batch;
- receive up to a bounded batch;
- atomically replace filters;
- query bus status;
- CAN-related lifecycle and health events.

No existing tag or enum meaning changes, and no field number is reused. Field-lock tests cover every new envelope variant and nested message. Unknown additive fields are tolerated when safe. Unknown required enums, malformed IDs/frames/timestamps/configurations, oversized batches, and unsupported operations fail closed as `runtime.protocol.invalid_message` or the appropriate capability/configuration error.

Ordinary CAN frames do not use unsolicited event envelopes. The broker exposes bounded pull-style receive:

```text
receive(session, max_frames: 1..=64, timeout) -> 1..=64 frames | timeout | lag
```

This keeps frame-rate backpressure separate from lifecycle events and preserves request correlation. Protobuf is appropriate because one CAN FD frame carries at most 64 payload bytes; v0.2 does not need a shared-memory data plane.

The relevant resource capabilities are additive and versioned:

- `can.classic/v1`;
- `can.fd/v1`;
- `can.configure/v1`;
- `can.error-frames/v1`;
- `can.rx-timestamp/v1`.

Clients negotiated to wire 1.0 cannot invoke CAN operations. Clients must check resource capabilities rather than infer support from adapter names.

## 10. Rust and Python clients

The in-process Rust interface and Rust broker client expose equivalent typed CAN operations. Broker sessions remain opaque; clients never receive OS sockets or PCAN handles.

The Python binding defines protobuf-independent immutable frame, ID, filter, timestamp, configuration, and bus-status models. It validates the same ranges and bounds before transmission and validates all peer data on receipt. Malformed peer data terminates the connection using the existing fail-closed terminal fan-out behavior.

Rust and Python cancellation, retry, close, terminal subscription, and queue-admission semantics match the v0.1 client contracts. A locally rejected retryable close or send admission does not lose the session handle.

## 11. Discovery and physical identity

All descriptors use the canonical core resolver and advertise CAN capabilities.

SocketCAN identity precedence is:

1. hardware serial or another stable udev/sysfs hardware identifier;
2. stable physical device path/topology evidence;
3. endpoint-derived interface name as Weak identity only.

The interface name (for example `can0`) is always an endpoint snapshot. `vcan` resources always have Weak identity.

PCAN identity uses stable vendor device ID, serial, or equivalent hardware evidence when available. A PCAN channel handle, enumeration order, or channel index alone is not Strong identity. If only transient evidence exists, the descriptor is Weak.

Duplicate persisted identities are ambiguous and fail closed. Selectors may require minimum identity quality. Hardware serials, topology paths, and vendor IDs are excluded from default logs.

## 12. Error model

Stable CAN error names include:

- `can.frame.invalid`;
- `can.configuration.mismatch`;
- `can.configuration.unsupported`;
- `can.receive.lagged`;
- `can.bus.off`;
- `can.bus.passive`;
- `can.adapter.unavailable`.

Existing generic errors remain authoritative for invalid protocol messages, queue admission, timeouts, cancellation, leases, stale fencing, sessions, permissions, and unavailable resources.

Every error produced after canonical resolution carries `resource_id`. OS codes use `platform_code`; documented PCAN-Basic statuses use `vendor_code`. Bounded context may include non-sensitive facts such as dropped count, requested bitrate, or supported limit. Stable decisions never parse debug messages or diagnostic details.

Missing optional PCAN-Basic libraries produce adapter-unavailable diagnostics without preventing unrelated adapters from starting. A deployment configuration may mark PCAN required, in which case broker startup fails before publishing its endpoint.

## 13. Broker composition and manifest

Broker features select independently composable adapters rather than a single Serial-versus-virtual switch. The manifest reports:

- broker `0.2.0`;
- wire major 1 and supported minor range `0..=1`;
- every compiled adapter;
- which optional runtime libraries are required;
- platform/architecture, MSRV, and artifact checksum as before.

Runtime adapter health is separate from compiled features. A compiled but unavailable optional PCAN adapter is visible through health/diagnostics without making Serial or SocketCAN unavailable. Required-adapter startup policy is explicit configuration, never inferred.

## 14. Testing and conformance

### 14.1 Core contract

- exact Standard/Extended ID bounds;
- Classic/FD/remote/error-frame invariants;
- exact payload, DLC, filter, batch, and queue bounds;
- timestamp source/domain preservation;
- decision-only errors and structured diagnostics.

### 14.2 Shared CAN conformance

Every adapter passes the same suite for each capability it advertises:

- Classical and CAN FD ordering and payload preservation;
- standard/extended IDs, remote frames, BRS, ESI, and error frames where supported;
- per-session filters and atomic replacement;
- multiple observers plus one controller;
- Maintenance exclusion and configuration verification;
- RX lag isolation and TX atomic backpressure;
- timeout, cancellation, close, owner loss, resource reuse, and fencing;
- bus status and timestamp behavior without fabricated support.

The virtual adapter provides deterministic hardware-free coverage and fault injection. It is a conformance adapter, not evidence that a platform adapter works natively.

### 14.3 Protocol, broker, and clients

- wire 1.0 legacy negotiation and wire 1.1 capability gating;
- additive tag locks and malformed fail-closed cases;
- bounded single/batch send and pull receive over real IPC;
- Rust/Python semantic parity and terminal fan-out;
- adapter coexistence, owner cleanup, and resource reuse;
- production and virtual broker manifests.

### 14.4 Platform adapter tests

- SocketCAN conversion, discovery/identity, netlink query/configure/restore, worker cleanup, and absence/permission errors;
- PCAN conversion, dynamic-library absence, documented vendor statuses, configuration, worker cleanup, and platform-code preservation;
- warnings-denied Linux and Windows target builds for the relevant code paths.

Physical/hardware tests are marked and excluded from the default suite.

## 15. Acceptance and qualification

Implementation completion requires:

- complete virtual CAN conformance;
- all hardware-free Rust, Python, broker, and wire tests;
- generated binding reproducibility;
- warnings-denied lint and supported cross-target compilation;
- explicit tests for missing PCAN runtime and unavailable SocketCAN configuration privileges;
- updated architecture, versioning, manifest, runbook, and v0.2 acceptance evidence.

Release qualification remains separate and requires fresh external evidence for:

- native Linux `vcan` and real SocketCAN execution;
- native Windows and Linux PCAN-Basic loading;
- PCAN hardware Classical/FD loopback, disconnect, bus-off, and cleanup;
- remote Linux/macOS/Windows CI as applicable.

The acceptance document reports these as pending until actually run. v0.2 implementation status must not be described as native/hardware-qualified without that evidence.

## 16. Documentation and compatibility

The implementation updates the architecture, responsibility-compatible hardware-class section, versioning/wire-minor contract, broker manifest documentation, CAN setup/runbooks, and v0.2 acceptance evidence in the same change series.

All changes remain additive to wire major 1. Public Rust/Python interfaces follow pre-1.0 SemVer. No planned capability is described as implemented until its code, conformance suite, client path, and broker path pass the final verification gate.

## 17. Resolved decisions

- Complete v0.2 includes Classical CAN and CAN FD, SocketCAN, PCAN, virtual conformance, broker, Rust client, and Python client.
- Only raw link-layer frames are in scope.
- Seeed HAL owns the stable interface and uses open-source CAN crates behind adapter seams.
- Attach never mutates configuration; Configure requires an exclusive Maintenance session.
- One actor owns each physical channel and multiplexes bounded per-session receive rings.
- Filters are session-local and software-authoritative; hardware filtering is semantics-preserving optimization only.
- RX overflow drops oldest and reports lag; TX overflow rejects the complete new admission.
- Timestamp origin and clock domain are explicit; no synchronization is implied.
- Frame data uses bounded protobuf request/response batches, not unsolicited events or shared memory.
- Native/hardware qualification is tracked separately from implementation completion.
