# Camera v0.4 design

## Scope

v0.4 adds a platform-neutral Camera capture interface to Seeed HAL. It covers camera discovery,
stable resource identity, exclusive capture sessions, format negotiation, capture controls,
timestamped frames, hotplug, cleanup, and a local shared-memory frame data plane for broker
clients. It preserves the responsibility boundary in
[HAL responsibility](../../contracts/hal-responsibility.md): this is hardware-class capture, not
product or device-protocol behavior.

The release does not include preview, display, encoding, image processing, recording, inference,
datasets, camera roles, or any other product semantics. Consumers that need those features receive
frames from HAL and implement them outside this workspace.

## Platform adapters and sessions

The native capture adapters are AVFoundation on macOS, V4L2 on Linux, and Media Foundation on
Windows. The first implementation must also include a deterministic virtual camera adapter in
`seeed-hal-testkit` so that contract and broker tests do not require hardware.

Camera resource descriptors persist physical identity and treat a device path or platform endpoint
as transient. A selector that finds zero or multiple matching cameras fails closed using the
existing structured resource errors. An unavailable native API, unimplemented adapter operation,
or unsupported configuration also fails closed with a stable structured error; it must not be
silently emulated or downgraded.

Every capture session is exclusive. The runtime holds one controlling lease and the broker retains
the native handle; a broker client has only an opaque session ID and lease generation. A second
HAL camera session for the same active resource is rejected even if a platform API would permit
multiple readers. Native adapters request operating-system exclusivity where available and report
any limitation, as required by the responsibility contract.

Native calls that can block run on an adapter-owned blocking worker or use native asynchronous I/O;
they never run on a Tokio executor worker. Closing, cancellation, lease expiry, disconnect, and
hot-unplug stop accepting capture work, retire the capture session, release mappings and platform
resources, and publish normal transport lifecycle events. This cleanup makes no claim about
application-level or physical safety.

## Capture format and bounds

The v0.4 common formats are `NV12`, `YUYV`, and `MJPEG`. Format selection is explicit: an open or
configure request supplies desired format and dimensions, and the adapter either returns the
selected supported format or fails closed. It must not substitute a different pixel format or
rescale frames without an explicit future contract addition.

The maximum negotiated coded dimensions are 4096 by 2160 pixels. Each published frame, including
its stored payload, is at most 24 MiB (25,165,824 bytes). Negotiation and every adapter write
validate both limits before allocating or publishing. A configuration whose worst-case frame can
exceed the 24 MiB limit is rejected. The shared ring has four slots by default and permits a
configured capacity from four through eight slots, inclusive. No unbounded frame, slot, queue, or
allocation is introduced.

Frame metadata includes at least the negotiated format, coded width and height, payload length,
monotonic capture timestamp, and monotonically increasing sequence. Adapters preserve the native
capture timestamp when it can be represented as a monotonic timestamp; otherwise they assign a
monotonic receipt timestamp and record that provenance in adapter diagnostics, never by inferring
wall-clock time.

## Broker protocol and shared-memory data plane

Camera control uses the existing length-delimited Protocol Buffers control plane at wire major 1,
minor 3. Camera additions are additive: new protobuf field numbers and envelope tags are never
reused. Peers negotiate major 1 and mutually select minor 3 before exposing any camera operation;
peers below minor 3 reject Camera entry points locally or at broker dispatch, respectively.

Protobuf transports discovery, open/configure/close, control requests and responses, capability
negotiation, and shared-ring descriptors. It never transports frame bytes. The broker establishes
a named shared-memory frame ring and returns only the mapping descriptor and required access
credential over the authenticated control connection.

The ring mapping name is generated from 256 bits of cryptographically secure randomness. A distinct
unpredictable capability token authorizes mapping access; the mapping name alone is insufficient.
Tokens are never logged and are released with the session. On POSIX the mapping is created with
mode `0600`. On Windows it has a protected DACL granting access only to the current user,
LocalSystem, and built-in Administrators. Mapping creation, opening, and validation fail closed
when the required protections cannot be applied or verified.

The data plane is cross-platform by contract: a named shared-memory mapping contains one fixed
header followed by fixed-size slots. The header records a magic value, layout version, total mapping
length, negotiated format and bounds, slot count, slot stride, and session-specific identity needed
to reject a mismatched or stale mapping. Each slot records state, sequence, generation, metadata,
payload length, and payload storage. Rust and Python clients validate every header and slot-layout
field, arithmetic overflow, bounds relation, and capability token before reading a payload.

Publication prevents torn reads: the producer writes payload and metadata first, then performs a
release publication of the slot sequence/state; readers acquire that publication before accepting
metadata or bytes. A reader rejects an incomplete, invalid, changed, or generation-mismatched slot
and retries through the documented latest-frame acquisition path rather than interpreting partially
written data. The exact atomics or platform synchronization primitive are confined to the
shared-memory crate, but must implement these acquire/release semantics on all supported targets.

From a native captured buffer to the shared ring there is at most one payload copy. Copies required
inside a platform capture API before the adapter receives the native buffer are outside this
adapter-to-ring bound and must be documented by the platform adapter. The broker and clients do
not make a second protobuf or frame-payload copy.

## Frame lifecycle and backpressure

Capture is latest-wins and non-blocking. When a new frame arrives, the producer selects a free
slot; if none is free, it overwrites only the oldest slot that is not borrowed. It never overwrites
a borrowed slot and never blocks native capture waiting for a consumer. If no writable slot exists,
the incoming frame is discarded. Each replacement or discarded incoming frame increments and
reports `dropped_count` through frame metadata or a structured capture-status query; the counter is
monotonic for the session and is reset only by opening a new session.

At most one slot may be pinned (borrowed) per session across an individual client. Before
`next_frame` waits for or acquires a new committed slot, its control-plane operation releases that
session's current pinned slot. It then pins the new slot if one is available; an existing pin never
causes a second acquire to fail. Release validates the session, slot sequence, and generation
before marking a slot reusable. Session closure invalidates all outstanding borrows.

The Rust API exposes a `FrameView` whose payload is lifetime-borrowed from the session acquisition
guard; safe Rust cannot retain that borrow after its guard is released. Calling `next_frame` first
ends the prior acquisition and releases its pin, so an old `FrameView` cannot remain usable after
the next acquisition. The Python API exposes `BorrowedFrame` with session/slot generation
validation before each payload access. `next_frame` releases the prior pin before obtaining a new
one, so the previous `BorrowedFrame` fails generation validation after that acquisition. It must
not provide a buffer-protocol object whose memory can escape for long-term use.
`BorrowedFrame.copy()` creates an owned Python bytes object and is the supported way to retain frame
data after the borrow is released or a subsequent frame is acquired.

## Capabilities and controls

Camera descriptors and negotiated sessions advertise only these standard hardware-class
capabilities:

- `camera.capture/v1` for exclusive format-negotiated capture;
- `camera.frames.shm/v1` for the named shared-memory frame ring;
- `camera.controls/v1` for standardized camera control discovery and operations.

The controls capability defines descriptor, get, set, and auto operations for exposure, gain,
white balance, and focus. A descriptor includes the standardized control kind, readable/writable
and auto-mode support, value representation, supported range or enumerated values, current-value
availability, and any adapter-defined non-decision diagnostic. `get` returns the current manual or
automatic value; `set` validates against the descriptor and changes the manual value; `auto`
enables or disables supported automatic control.

Each operation is separately capability-gated. If a platform or selected camera lacks a control or
the requested auto/manual operation, it fails closed with a structured
unsupported-capability/configuration error. The HAL must not synthesize a value, retain a fake
software control, or convert a control request into device-specific behavior.

## Unsafe boundary

`seeed-hal-runtime`, `seeed-hal-broker`, `seeed-hal-client`, core, protocol, and language-client
logic use no `unsafe`. Any required `unsafe` is confined to the shared-memory crate and the three
platform-adapter crates. Every unsafe block has an immediately preceding `// SAFETY:` comment that
states its upheld invariant, and has a focused test for that invariant or an explicit cited
upstream platform contract where a test cannot exercise it. Safe wrappers expose validated
ownership, mapping layout, and synchronization behavior without leaking raw handles or pointers
to runtime, broker, or client code.

## Verification and external qualification

Hardware-free verification includes format and limit contract tests; virtual-adapter conformance;
exclusive lease and stale-generation tests; latest-wins, pinning, drop-counter, and torn-write
tests; shared-memory header/layout/security validation; Rust lifetime API tests; Python
generation, escape-prevention, and `copy()` tests; wire-major/minor and protobuf field-tag locks;
broker black-box lifecycle tests; and focused unsafe-boundary tests.

Default CI does not claim native camera qualification. v0.4 release qualification additionally
requires explicit external evidence from real cameras on macOS AVFoundation, Linux V4L2, and
Windows Media Foundation. That evidence must cover discovery/identity, exclusive capture, each
available approved format, maximum-bound rejection, control descriptor/get/set/auto behavior,
hot-unplug cleanup, shared-memory access protections, and no-blocking capture under a pinned
consumer. Platform availability limits must be recorded as qualification results, not hidden by
fallback behavior.

## Acceptance criteria

v0.4 is complete only when the virtual adapter passes the shared camera conformance suite; broker
and both language clients negotiate major 1/minor 3 and exchange control messages without frame
bytes; all frame limits and ring capacities are enforced; borrowed slots are never overwritten;
drop accounting is observable; mappings validate and enforce platform access protections; unsafe is
limited and justified as specified; and external qualification evidence is kept distinct from
hardware-free test results.
